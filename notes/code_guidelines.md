# Правила чистки кода

Составлено по двум документам Google и по инвариантам этого проекта:
- Google Python Style Guide — https://google.github.io/styleguide/pyguide.html
- Google Engineering Practices, Code Review — https://google.github.io/eng-practices/review/

Ниже — пересказ пунктов, нужных для нашей чистки, а не копия оригиналов.

## Инварианты проекта (нарушать нельзя)

1. **Поведение не меняется.** После каждого изменения `python -m scripts.golden_outputs` должен печатать `golden outputs identical`. Если правка неизбежно меняет арифметику с плавающей точкой (векторизация, другой порядок суммирования), её не делать, а записать в отчёт как предложение.
2. `python -m pytest tests/ -q` — все тесты проходят.
3. Форматы на диске совместимы:
   - кэш траекторий `data/trajectories` (ключ `trajectory_cache_key`, сериализация `stores.py`);
   - чекпойнты в `checkpoints/` (`from_bytes`);
   - CSV в `experiments/results/` не трогать.
4. Скрипты экспериментов, на которые ссылаются статьи и каталог (`src/application/experiment_catalog.py`), не удалять. Их можно упрощать и переводить на общие функции, сохраняя запуск `python -m experiments.<имя>` и те же CSV на выходе.
5. Тексты статей и документа (`paper/`) не трогать.

## Стиль (Google Python Style Guide, кратко)

- **Импорты.**
  - Импортировать модули и пакеты, а не отдельные имена; исключение — `typing`.
  - Полные пути от корня пакета, без относительных импортов в новом коде.
  - Группы: `__future__`, стандартная библиотека, сторонние, свои; внутри групп — по алфавиту.
  - Не полагаться на `sys.path.insert`: эксперименты запускаются через `python -m`.
- **Функции.**
  - Короткие и с одной задачей; функции длиннее ~40 строк разбивать.
  - Вложенные функции — только чтобы замкнуть локальную переменную.
  - Вместо `@staticmethod` — функции модуля.
- **Аргументы по умолчанию.** Никаких изменяемых (`[]`, `{}`): только `None` и создание внутри функции.
- **Глобальное состояние.** Не заводить изменяемых глобальных переменных; константы модуля — `CAPS_WITH_UNDER`.
- **Исключения.**
  - Встроенные, где подходят (`ValueError` и т.п.).
  - `assert` — не для проверки входных данных.
  - Не ловить `Exception` без необходимости; блоки `try` держать маленькими.
- **Истинность.**
  - Пустые контейнеры проверять через `if not x`, `None` — через `is None`.
  - Пустые массивы NumPy — через `.size`.
- **Аннотации типов.** Для публичного API и сложного кода; `X | None` вместо неявного `Optional`.
- **Имена.**
  - `module_name`, `ClassName`, `function_name`, `CONSTANT`, `_private`.
  - Без однобуквенных и непонятных сокращений, кроме устоявшихся обозначений из физики (`J`, `rho`, `dt`, `T2`) — их можно, с пояснением в docstring.
- **Docstrings.**
  - У каждого модуля, публичного класса и нетривиальной функции.
  - Первая строка — краткое описание (≤ 80 символов), затем секции `Args:`, `Returns:`, `Raises:`, у классов — `Attributes:` для публичных полей.
  - Описывают, *как вызывать и что получится*, а не реализацию.
- **Комментарии.**
  - Объясняют *почему*, а не *что*.
  - Устаревшие комментарии удалять.
  - Ссылки на «task 19» и историю правок убрать.
- **Формат.**
  - Строки ≤ 80 символов; переносы внутри скобок, без `\`.
  - Без выравнивания пробелами по вертикали.
  - Две пустые строки между определениями верхнего уровня.
- **Доступ к защищённым членам.** Не обращаться к `_private` чужого класса или модуля (например, `NoiseSweepUseCase._add_noise`, `QuTipSimulator._sudden_death_time`, `predictor._feature_mean` из экспериментов). Если это нужно снаружи, сделать публичную функцию.
- **Отделять стилевые изменения от смысловых** и не смешивать их в одном коммите, где это возможно.
- **Решать сегодняшнюю задачу без лишней абстракции.** Не вводить классы и параметры «на будущее».

## Что проверяет ревьюер (Google Code Review Guide, кратко)

- **Дизайн:**
  - на своём ли месте код;
  - понятны ли связи между частями;
  - нет ли переусложнения.
- **Функциональность.** Делает ли код то, что задумано; крайние случаи.
- **Сложность.** Можно ли быстро понять каждую строку, функцию, класс.
- **Тесты.** Падают ли они, если код сломать; тесты — тоже код, который надо поддерживать.
- **Имена, комментарии, стиль, согласованность с остальным кодом.**
- **Документация.** README и Makefile обновлены, если изменился способ запуска.
- **Каждая строка изменения прочитана.**
- **Контекст.** Изменение смотрится в составе всего файла и системы. Не принимать того, что ухудшает здоровье кода.
- **Стандарт одобрения.** Изменение принимается, если оно явно улучшает код, даже если не идеально. Мелочи помечаются «Nit:» и не блокируют.
